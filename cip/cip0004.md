# CIP-0004: MkDocs Material documentation site and consumer cookbooks

## Status

- [x] Proposed
- [x] Accepted
- [x] In Progress
- [x] Implemented
- [ ] Closed

## Summary

Publish multilogue as a **MkDocs Material** site with mkdocstrings API pages and cookbooks that show how to build `ai-dialogue-formats`-style and `pub-dialogue`-style consumer packages. This is the documentation / compression stage for CIP-0001–0003 (REQ-0007).

## Motivation

Notebooks teach by doing; CIPs record design. Neither is a stable onboarding surface for a third study. We need formal docs that compress the method and show the package boundary: what lives in multilogue versus what stays in the consumer.

## Detailed Description

### Choice: MkDocs Material (not Sphinx)

| Option | Pros | Cons |
|--------|------|------|
| **MkDocs + Material + mkdocstrings** | Markdown-native (matches existing `docs/*.md` and CIP compression); Material is the current default for modern Python library docs; fast local preview; GitHub Pages is one workflow | Less TeX-heavy than Sphinx |
| Sphinx + MyST + Furo | Common in academic Python; richer cross-refs | Heavier config; would rewrite Markdown into a second toolchain |

**Decision:** MkDocs Material. Multilogue is a methodology library whose prose already lives in Markdown. We keep Sphinx out unless we later need heavy math publishing. Notebooks remain pedagogical; the site is the durable reference. Pin `mkdocs>=1.6,<2` until Material documents a MkDocs 2 migration path.

### Site shape

```
docs/
  index.md                 # landing
  getting-started.md
  methodology.md           # AAA + shared steps (compress CIP-0001)
  concepts/                # units, checkpoints, weighting, multiverse
  guide/                   # Access / Assess / Address how-tos
  cookbooks/
    consumer-skeleton.md   # generic package layout
    ai-dialogue-formats.md # formats-comparison consumer
    pub-dialogue.md        # multi-technology consultation consumer
  api/                     # mkdocstrings
  notebooks.md
  migration.md
mkdocs.yml
```

### Consumer cookbooks (no private data)

Examples use **synthetic units** and `FakeClient` only. They name the real consumer repos as *targets* (what to keep vs call) and give a minimal package layout (`access.py` / `assess.py` / `address.py` or equivalent) so a new author can recreate that shape.

### Hosting

- Local: `mkdocs serve` / `mkdocs build`
- Optional: GitHub Pages via `.github/workflows/docs.yml` on `main`

### Compression

This CIP compresses CIP-0001 (method boundaries), CIP-0002 (Access loaders), and CIP-0003 (notebooks pointer) into the formal site. After validation, mark those CIPs `compressed: true` when closing this one.

## Implementation Plan

1. Add REQ-0007 and this CIP
2. Add `mkdocs.yml`, docs extras in `pyproject.toml`, `site/` gitignore
3. Write concept/guide/cookbook pages; wire mkdocstrings
4. Add Pages workflow; link README
5. `mkdocs build --strict` (or near-strict) in CI/local verify

## Backward Compatibility

Additive. Existing `docs/methodology.md` and `docs/migration.md` remain paths on the site. No API changes.

## Testing Strategy

- `mkdocs build` must succeed
- Cookbook code snippets must match public APIs (smoke against package imports where practical)
- No private dialogue strings in `docs/`
